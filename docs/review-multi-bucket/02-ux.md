# UX Lane — Multi-Bucket + Account Management Redesign

Reviewer: UX lane, 5-expert design panel. Design only — no source changed.
Scope: `src/components/App.jsx` (splash ~1265-1344, connected shell ~1345-1428, header
~1201-1252, `handleSelectProfile`/`handleSaveProfile`/`handleDisconnect` ~1033-1132,
375-407), `src/components/ProfilePicker.jsx` (full), `src/components/CredentialForm.jsx`
(full), `src/components/Browser.jsx` (header/breadcrumb area), `src/styles/main.css`
(sidebar/profile-picker/mobile rules), `docs/review-v1.14.0/05-roadmap-ux.md`,
`docs/design-multiprofile.md` (original v1.13.0 plan — explicitly deferred "profile
management in a dedicated modal" and "multiple simultaneously connected accounts,"
which is exactly this redesign's job).

All line references are to the file as read for this review; treat them as pointers,
not guarantees against drift.

---

## Flow walked

I walked two personas against the **current** app (source-read, not live-clicked —
noted per finding):

**(a) Brand-new user**, arriving with one B2 bucket's Key ID/Secret. Goal: get to
their files.

**(b) Returning user with 3 buckets across 2 accounts** (say: B2 account with
`photos` and `backups`, and an AWS account with `client-assets`). Goal: check
something in `client-assets`, then go back to `photos`.

---

## 1. Current friction, named concretely

### New user (a)

1. Lands on splash (`App.jsx:1267`). `ProfilePicker` renders nothing but a
   greyed-out "Save as profile…" ghost button (`ProfilePicker.jsx:18-28`) — a
   control that's disabled until the form below is filled, sitting *above* the form
   it depends on. First-glance confusion: a button with no visible reason to exist
   yet, disabled, no explanation why. Minor, but it's the very first thing rendered.
2. Fills in `CredentialForm`: Endpoint, Bucket, Base folder, Key ID, Secret Key,
   Provider Override, Region — 5 required fields plus 2 conditional ones, one
   scrolling form (`CredentialForm.jsx:228-380`). No sense of progress, no "you're
   basically done" signal. Bucketer is honest that this is a one-time setup cost —
   fine for a once-a-year mental model, but it is genuinely the *first* thing every
   new bucket forces, repeatedly, with no shortcut once a sibling bucket on the same
   account already exists (see friction 4b below).
3. Hits Connect. No "save this?" nudge — the profile-save control is a ghost button
   above the form the user has to notice on their own, not part of the success path.
   A first-time user who doesn't spot it gets no saved profile, and next session
   starts from a blank form again. **This is a shortest-path violation**: saving
   should be the default, not an opt-in the user has to discover.

### Returning user (b), 3 buckets / 2 accounts

4. **Flat list, no grouping.** `ProfilePicker` renders `profiles` as one
   undifferentiated `<ul class="profile-list">` (`ProfilePicker.jsx:50-78`). With 3
   buckets the user sees three rows — `B2 — photos`, `B2 — backups`,
   `AWS — client-assets` (name/hint format from `profileHint()`,
   `ProfilePicker.jsx:106-111`) — with no visual indication that the first two share
   one account. At 3 buckets this is a mild inconvenience; the design brief's own
   framing ("2 accounts") makes clear this must scale past 3, and a flat list
   degrades linearly with bucket count while grouping degrades with account count
   only. **This is the single largest structural gap** the redesign exists to close.
5. **No "add a bucket to the account I'm already looking at."** Because there is no
   account entity in the UI, adding `client-assets`'s sibling bucket to the AWS
   account means retyping Endpoint, Key ID, Secret Key, Provider, and Region from
   scratch in `CredentialForm` — the app has no path from "I already told you this
   endpoint and key" to "now just tell me the new bucket name." (The data model
   *does* support this — `findOrCreateCredential`, `App.jsx:1060-1065` — but no UI
   surface exposes it. This is a UI gap on top of a ready backend, which is the
   cheapest kind of gap to close.)
6. **Switching requires leaving the workspace.** While connected, the sidebar shows
   only a reconnect `CredentialForm` (`App.jsx:1354-1358`) and the active
   connection's bare name (`profile-active-name`, `App.jsx:1349-1353`) — **no
   `ProfilePicker`, no list of the other 2 buckets, nothing clickable to switch to
   another saved bucket.** The only way to reach another bucket is the header
   **"Disconnect"** button (`App.jsx:1244-1246`), which tears down the whole
   connected view and returns to the splash screen (`handleDisconnect`,
   `App.jsx:380-407`) — at which point `ProfilePicker` reappears and the user can
   finally pick `photos`. **To go from `client-assets` to `photos` today: click
   Disconnect → find `photos` in the flat list → click it → re-type the Secret Key
   (session-only, cleared on every reconnect since the vault is gated off per
   memory) → click Connect → wait for the capability probe.** That is 1 destructive-
   feeling click, 1 list scan, 1 click, 1 full credential re-entry, 1 submit, 1
   network round-trip — for what the user experiences as "look at a different
   bucket." Compare to a browser tab switch, which is what the mental model this
   redesign targets implies it should feel like.
7. **"Disconnect" is scary-sounding for what is actually "switch."** The single
   button that performs bucket-switching is labeled and styled exactly like a
   sign-out action, next to no confirmation, when its real job for 80% of clicks
   will be "let me look at my other bucket." This is a **least-surprise** issue: the
   control's name promises something more final than what most users will use it
   for.
8. **Secret re-prompt on every switch**, because there is no vault (gated off).
   This is a real constraint the redesign must design *around*, not eliminate — but
   today it's compounded by friction 6: a user bouncing between 2 buckets in one
   session retypes a secret every single bounce. That compounding is a UX cost the
   redesign can reduce even without touching the vault: fewer round-trips through
   the splash screen per switch means fewer secret prompts feel like "the app asked
   again" versus "the app makes me start over."
9. **Delete-from-list has no account-aware messaging.** `ProfilePicker`'s per-row
   delete asks a flat "Delete?" (`ProfilePicker.jsx:56-67`) with no mention of
   whether deleting the last bucket under an account also drops the account's
   stored credential, or whether the credential (Key ID/endpoint) survives for the
   next bucket. A grouped manager must answer "what happens to the account" when
   its last bucket is deleted, and say so before the user commits.

**Vocabulary friction noted separately in §5** — worth flagging here too because it
compounds every finding above: the app calls this list "profiles" in the UI heading
(`ProfilePicker.jsx:49`, "Saved profiles"), "Saved Profiles" in `StorageModal.jsx`,
but **"Your buckets"** in `VaultUnlock.jsx:75` — three different words for the same
list of things depending which screen you're on, none of which is "account" or
"bucket" consistently.

## 2. The accounts → buckets manager

### Where it lives

**Not a new top-level screen, not buried in Settings.** It replaces
`ProfilePicker` in both of its current mount points — the splash screen
(`App.jsx:1273-1280`) and (newly) the sidebar drawer, so switching never requires
leaving the connected view (closes friction 6). One component, two contexts:

- **Splash context**: full-width, primary content of the page — this is the
  disconnected user's *only* task, so it should look like the main event, not a
  widget above a form.
- **Sidebar context**: same component, narrower, inside the existing translateX
  drawer (`.sidebar`, `main.css:109-125`) — reachable via the existing hamburger
  (`App.jsx:1202-1210`) at any time while connected. No new drawer, no new
  interaction pattern — reuse what's already there.

### Structure

A two-level disclosure tree: **account** (credential) as the parent row, **bucket**
(connection) as children. Collapsed by default per account except the account
containing the currently-active bucket, which starts expanded.

```
┌─ Accounts & buckets ──────────────────────────────────────┐
│                                                             │
│  ▾ Backblaze B2 · keyID 0042abc…            [+ bucket]     │
│      ● photos                          (active)            │
│        backups                                             │
│                                                             │
│  ▸ AWS S3 · keyID AKIA7f2…                  [+ bucket]     │
│                                                             │
│  + Add account…                                            │
└─────────────────────────────────────────────────────────────┘
```

- **Account row**: provider label + endpoint or masked Key ID as the
  disambiguator (two AWS accounts need something better than "AWS S3" ×2 — the Key
  ID's last 4-6 chars, already how the app truncates elsewhere in spirit, is
  enough without echoing the whole secret-adjacent string). A `[+ bucket]`
  affordance on hover/focus — click it and the flow is: **name-the-bucket only**,
  reusing the account's stored endpoint/Key ID/provider/region already resolved by
  `findOrCreateCredential` (`App.jsx:1060-1065`) under the hood — no retyping
  anything the account already established. This directly closes friction 5. The
  Secret Key is still required at add-time (it's never stored), but only once, not
  per field.
- **Bucket row**: name, a dot/highlight for "this is the active one," click
  anywhere on the row to switch (see §4). A small delete affordance appears on
  hover, same confirm-inline pattern already used (`ProfilePicker.jsx:56-67`) — keep
  that pattern, it works and is already familiar.
- **"+ Add account…"** is the *only* place a fresh `CredentialForm` (Endpoint,
  Key ID, Secret, Provider, Region) appears in the manager. It opens the existing
  form, unchanged, just now explicitly framed as "new account" rather than being
  the default/only path.

### Empty states

- **Zero accounts** (true first-run): the manager collapses to exactly what exists
  today — `CredentialForm` front and center, no tree chrome to be confused by. Don't
  show an empty tree with a "+ Add account" button above a form that already *is*
  the way to add an account — that's a duplicate control for a first-run user who
  has nothing to manage yet. (This matches `ProfilePicker.jsx:18-28`'s existing
  `profiles.length === 0` branch — keep that instinct, replace its contents.)
- **Account exists, zero buckets under it** (shouldn't normally happen once
  save-by-default ships, §1 finding 3 — but reachable if the user deletes every
  bucket under an account without deleting the account): show the account row with
  an inline "No buckets saved yet — [+ bucket]" instead of silently disappearing.
  An account with no buckets is a dangling credential the user forgot about; making
  it visible (not auto-deleted) lets them either add a bucket to it or explicitly
  remove it — silent auto-delete would be a surprise the size of "where did my
  saved login go."

## 3. The quick-switch / tab-bar

### Where and what

A slim strip in the **app header**, between the logo and the existing status/action
buttons (`App.jsx:1211-1219` is the insertion point — currently logo → spacer →
provider label → status badge). Shows only *recently-used* buckets (last ~5,
most-recent-first, current one pinned first) — not the full account tree; the
manager is the source of truth, the tab bar is a shortcut to what you just used.

```
┌────────────────────────────────────────────────────────────────────────┐
│ [☰]  🪣 Bucketer   [B2 · photos ✕] [B2 · backups] [AWS · client-assets] │
│                     ▔▔▔▔▔▔▔▔▔▔▔▔▔                    ⊕ Switch…         │
└────────────────────────────────────────────────────────────────────────┘
```

- Each tab shows **provider + bucket name** (the same `profileHint()` shape
  already computed, `ProfilePicker.jsx:106-111` — reuse it verbatim, don't invent a
  new label format). Account is implied by provider+bucket pairing for most users;
  it does *not* need to repeat the Key ID in the tab — that's manager-level detail,
  the tab bar's job is speed, not disambiguation.
- Active tab is visually pinned/underlined, matches the existing `.profile-row-
  selected` accent treatment (`main.css:1105`) for visual consistency with the
  manager, not a brand-new "active" visual language.
- An overflow "⊕ Switch…" affordance (not a literal `+`) at the end opens the
  manager (as a popover from the header on desktop, or the sidebar drawer on
  mobile — see §7) when the user wants a bucket that's fallen out of the recents
  window.
- **No close (✕) on the active tab** in the strip's normal state — closing a tab
  you're looking at is a "disconnect," which already has a place (§1 finding 7
  addresses renaming that action). A ✕ on *inactive* tabs is fine (removes it from
  the recents strip only, does not delete the saved bucket) but should not read as
  destructive since it isn't.

### How it coexists with the manager

The tab bar is **derived from, not a duplicate of**, the manager's saved buckets —
it's a most-recently-used projection, never an independent list. Deleting a bucket
in the manager removes its tab immediately; a tab click never creates a bucket that
doesn't already exist in the manager. This one-way relationship (manager = source of
truth, tabs = view) is what keeps the "both" mental model from becoming two things
the user has to keep in sync in their head.

## 4. Switching flow

**Target flow, tab already visible (the common case within one session):**

1. Click the `backups` tab in the header.
2. If a secret is already held for that bucket's account this session (e.g. the
   user already unlocked it once, or two buckets share one account and the secret
   was entered for the sibling already this session) → **switch is instant**, no
   modal, Browser remounts against the new bucket. **1 click.**
3. If not (first switch to that account this session, vault gated off) → a small
   inline prompt for just the Secret Key (not the full `CredentialForm` — endpoint/
   key ID/provider are already known) appears anchored under the tab, not a full
   splash-screen round-trip. **1 click + 1 field + Enter.**

**Target flow, bucket not in recents (via manager):**

1. Click ⊕ Switch… or open the sidebar.
2. Click the bucket row in the tree (auto-expanding its account if collapsed).
3. Same secret-prompt-if-needed step as above.

**Contrast with today:** current path for *any* switch while connected is
Disconnect → scan flat list → click → full `CredentialForm` remount → retype
secret → Connect → wait (§1 finding 6, ~5-6 discrete steps and a full page-level
context loss). Target path collapses the common case to **1 click** and the
worst case (secret needed) to **1 click + 1 field**, and never leaves the
connected view — no Browser unmount/remount flash to the splash screen, no lost
scroll position or open panels in the surrounding UI (MasterQueue, UploadQueue,
etc. — `App.jsx:1396-1428` — currently these implicitly reset because the whole
connected shell unmounts on Disconnect; the new flow should make explicit whether
they reset on a bucket switch too, since a switch is a *bucket* change but the
upload queue etc. are not obviously bucket-scoped in the current single-bucket
model — flagging this as an implementation question for the architect lane, not
resolving it here).

## 5. Vocabulary

The app is inconsistent today: "Saved profiles" (`ProfilePicker.jsx:49`), "Saved
Profiles" (`StorageModal.jsx:209`), but **"Your buckets"** (`VaultUnlock.jsx:75`) —
three labels for what is conceptually the same list, with internal variable/function
names already having moved to `connection`/`connections` (`App.jsx` throughout,
`saveConnectionRecord`, `deleteConnectionRecord`) while the UI-facing strings lag
behind at "profile." This drift is exactly the kind of thing that confuses a
returning user trying to find "that thing I saved" — they don't know which word the
UI will use where.

**Recommendation — decisive, not hedged:**

| Concept | User-facing word | Not |
|---|---|---|
| The credential (endpoint + key ID + provider + region) | **Account** | "profile," "credential," "connection" |
| One `{credential, bucket, basePrefix}` pairing, the thing you click to browse | **Bucket** (when unambiguous) or **saved bucket** in list contexts | "profile," "connection" |
| The union of account+bucket as a stored record | Never surfaced as a noun — the UI shows *accounts* and *buckets*, not "connections." Users don't think in the app's join-table; don't make them. | "connection," "profile" |
| The header/manager view | **"Accounts & buckets"** (manager) / no label needed on the tab strip itself | "Profiles" |
| The action of adding a new bucket to an existing account | **"Add a bucket"** | "New profile," "New connection" |
| The action of adding a wholly new credential | **"Add an account"** | "New profile" |

Rationale: "profile" is a term of art the app invented and never explains — a new
user has no prior model for what a "profile" is in an S3 tool. "Account" and
"bucket" are both terms the user already brought with them (their storage
provider's own dashboard calls it a bucket; "account" is the natural word for "the
credential that owns several buckets"). This also happens to match S3's own
vocabulary, which reduces the translation tax between Bucketer's UI and whatever
setup docs or provider dashboard the user is tabbing back and forth to.

**Cut "profile" from every UI string** (list heading, empty-state button, delete
confirm, `StorageModal` section) as part of this redesign — do not leave the old
word in some screens and the new one in others; that recreates exactly the drift
this section is flagging.

## 6. The #40 admin line

GitLab #40 declined "bucket list / create / admin console" as a scope violation:
Bucketer must never offer to enumerate a provider account's buckets via a
privileged/admin call, create buckets, or otherwise act as a bucket-management
console. The manager designed in §2 must stay strictly on the allowed side of that
line. Concretely:

**Allowed — this is what §2 builds:**
- Show buckets **the user has explicitly told Bucketer about** by typing a bucket
  name into a form (today's `CredentialForm.jsx:252-267`, unchanged) — this is
  local, client-stored bookkeeping of the user's own past input, not a discovery
  call against the provider.
- Group those self-entered buckets under the account (credential) the user also
  typed in. This is presentation of data the user already gave the app, not a new
  capability against the S3 API.
- "+ Add bucket" under an account (§2) still requires the user to **type the
  bucket name themselves** — it pre-fills the *credential* fields from the
  account, never calls `ListBuckets` or any admin/discovery API to suggest bucket
  names. This is the load-bearing distinction: convenience on the credential side
  (already-known, already-typed fields) is fine; any suggestion sourced from a
  provider API call the user didn't explicitly ask this specific action to make
  would cross into "the app is enumerating my account," which is #40's declined
  shape.

**Must NOT offer, anywhere in this redesign:**
- A "browse other buckets on this account" or "discover buckets" button that
  calls `ListBuckets` (or equivalent) against the provider. If a user has 10
  buckets on one AWS account and has only ever told Bucketer about 2, the manager
  shows exactly those 2 — it does not offer to go find the other 8.
- Bucket creation ("+ New bucket" that actually calls `CreateBucket`). "+ Add
  bucket" in §2 only ever adds a *local record* of a bucket that must already
  exist — the CORS setup guide (`SetupGuide.jsx`) already assumes the bucket
  exists and CORS is configured on it by the user via their provider's own
  tooling; nothing in this redesign changes that assumption.
- Any UI copy implying Bucketer "manages your account" (e.g. don't write "Manage
  your AWS account" as a section header — write "Buckets you've added" or
  similar, phrasing that keeps the locus of control on the user's own past
  actions, not on Bucketer acting as an admin surface).

If a future request asks for "show me all my buckets on this account" (true
discovery), that is explicitly out of scope for this redesign and should be
bounced back to product with an explicit #40-conflict flag, not quietly
implemented because the manager UI made it look easy to bolt on.

## 7. Mobile

Current state (verified in `main.css`): the sidebar is a `position: absolute`
drawer, `translateX(-100%)` when closed, on **every** viewport width — it is not a
desktop-persistent rail with a mobile-only collapse; `sidebarOpen` defaults to
`false` always (`App.jsx:165`) and there is exactly one width-based breakpoint,
`max-width: 640px` (`main.css:1156`), which handles header wrapping, modal sizing,
and file-table column reflow — it does not currently touch `.sidebar` or
`.profile-picker` layout at all.

This is actually favorable for the redesign: **the sidebar is already a slide-over
overlay on desktop too**, so putting the manager there costs nothing extra on
mobile — there's no "desktop rail becomes a drawer on mobile" transition to design,
because it's a drawer everywhere already. Two things do need explicit mobile
treatment:

- **The tab bar (§3) does not fit a phone header.** At ≤640px, collapse the header
  tab strip entirely (same wrapping instinct already applied to `.app-header` at
  `main.css:1157-1159`) and replace it with a single compact control — active
  bucket name + a chevron — that opens the manager drawer directly to its
  "recents" view (the same MRU list, just rendered as rows in the drawer instead
  of tabs in the header). Don't try to horizontally-scroll a tab strip on a phone;
  that's a discoverability dead end (nothing signals there's more to scroll to).
- **Touch targets in the manager tree.** The existing `.profile-row` pattern
  (`main.css:1098-1113`) has no enforced minimum height — the ~640px file-table
  slice already had to explicitly enlarge tap targets for the same reason
  (`.file-table .btn-sm { padding: .5rem .55rem; }`, `main.css:1177`). The manager's
  account rows, bucket rows, and their inline delete/add affordances need the same
  pass — 44px minimum row height at this breakpoint, not inherited desktop padding.
- **The account-row disclosure triangle (▾/▸) needs a real tap target**, not just
  the glyph — a common mobile miss is making the expand/collapse hit-area exactly
  the width of the tiny triangle character. Make the whole account row (not just
  the icon) toggle expand/collapse on tap; clicking the bucket rows underneath
  should not also be reachable by mis-tapping the parent.

No new breakpoint architecture is needed — extend the existing `max-width: 640px`
block, matching the file's established pattern instead of inventing a second one.

## RECOMMENDATION

Ship exactly this, in this shape:

1. **One `AccountsManager` component** replaces `ProfilePicker` in both its splash
   and (new) sidebar mount points. Two-level tree: account → buckets, collapsed-
   by-default except the active account. "+ bucket" per account reuses
   `findOrCreateCredential`; "+ Add account" opens the existing `CredentialForm`
   unchanged.
2. **A recents tab strip in the header**, MRU-ordered, derived from (never
   duplicating) the manager's saved buckets. Click = switch; overflow control opens
   the manager.
3. **Switching never routes through Disconnect/splash.** A bucket click swaps
   credentials + remounts `Browser` in place; secret re-prompt (still required,
   vault gated off) is an inline field, not a full form.
4. **Rename "Disconnect"** to something that reads as "leave Bucketer" (e.g.
   "Sign out" or "Close connection" — pick one, but stop using the same word for
   "switch bucket" and "leave the app," since today there's only one button doing
   both jobs).
5. **Vocabulary sweep**: "profile" → "account"/"bucket" everywhere, including
   `StorageModal.jsx` and `VaultUnlock.jsx`'s already-inconsistent "Your buckets."
6. **Save-by-default on first successful Connect** (kills friction #3) — the
   ghost "Save as profile…" button becomes unnecessary for the common case; keep
   an explicit "Forget this bucket" as the reversal, not "remembering was opt-in."

### Explicitly cut (YAGNI for this pass)

- **True bucket discovery (`ListBuckets`).** Out of scope by #40; don't build a
  "discover buckets on this account" affordance even as a stub or disabled button
  — a visibly-disabled admin-shaped control is still an admin-shaped promise.
- **Drag-to-reorder tabs or tree rows.** MRU ordering for tabs and alphabetical (or
  insertion-order) for the tree is enough; manual reordering is a power-user
  feature nobody asked for in the brief.
- **Renaming an account** (as distinct from renaming a bucket, which
  `handleSaveProfile`'s existing update-in-place already supports). The account
  row's label is provider + masked key ID — functional, not precious. If two
  same-provider accounts need disambiguating names later, that's a follow-up, not
  part of shipping the tree.
- **Cross-account bulk actions** ("move a file between two different accounts'
  buckets" or similar). This redesign is about *navigating between* accounts/
  buckets, not operating across them simultaneously — keep the one-active-
  connection-at-a-time model exactly as `App.jsx` already implements it; only the
  *path to switch* changes, not the concurrency model.
- **A dedicated full-page "Accounts" settings screen** separate from the drawer/
  splash manager. One component, two mount contexts (§2) is sufficient; a third
  surface duplicating the same tree adds a place for the two to drift out of sync.

## Questions for real users

- Does "Account" read as clearly non-scary to a user who has never had a
  concept of "logging in" to Bucketer (there's no server-side account — is
  "account" going to imply one exists)? Worth a 5-user word-test against
  "Provider" or "Key" as alternatives before committing.
- Is 5 recent tabs the right MRU depth, or do actual multi-bucket users (the
  brief's "3 buckets / 2 accounts" persona, and beyond) want more/fewer visible
  at once before reaching for the manager?
- For the inline secret re-prompt on tab switch (§4 step 3): does anchoring it
  under the clicked tab read as clearly "for this bucket," or does it need an
  explicit bucket name repeated in the prompt to avoid "wait, which bucket am I
  unlocking" confusion when switching quickly between two accounts?
- Mobile: is a MRU-list-in-drawer an acceptable substitute for tabs, or do phone
  users of this app switch buckets often enough that even that costs too many
  taps relative to desktop's one-click tab? (No usage data exists yet — this
  redesign predates real multi-bucket users.)

---

## Verdict

**Design-stage — not yet gradable as ready/needs-changes** (no running surface
exists; this document IS the input the frontend lane builds from). The
recommendation above is internally coherent, reuses existing visual/interaction
patterns (`.profile-row` styling, the inline-confirm delete pattern, the existing
sidebar drawer, the existing MRU-free `profileHint()` label format) rather than
inventing new ones, and stays inside the #40 boundary throughout. The one open
risk worth flagging to the architect lane before implementation starts: whether a
bucket switch should reset the upload queue / master queue / open panels
(`App.jsx:1396-1428`) the way a full Disconnect does today — that's a state-
management question this UX lane surfaces but does not resolve.
