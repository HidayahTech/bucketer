# Endpoint ↔ Region Bidirectional Inference — Design Spec

**Date:** 2026-06-07
**Status:** Approved

---

## Problem

The credential form has a one-way relationship between endpoint and region: region is
extracted from the endpoint URL and shown as a hint, but the extraction result is not
surfaced as an editable field, and no inference runs in the other direction. A user who
selects a provider from the provider-override dropdown and types a region into the region
field gets nothing in the endpoint field.

The form also conditionally hides the region field when the endpoint embeds the region
(`needsRegion = !regionHint && form.endpoint`), making the auto-extracted value invisible
and non-overridable without changing the endpoint.

---

## Design

### Approach: bidirectional inference with inferred marker

Two live inference directions:

1. **Endpoint → region**: when the endpoint field changes to a URL containing an
   extractable region (B2, Wasabi, AWS, DO Spaces), the region field is auto-filled.
   The region field shows an "Auto-filled from endpoint URL" hint while inferred.

2. **Provider + region → endpoint**: when the region field changes and a provider is
   known (from the provider-override dropdown or auto-detected from the current endpoint),
   `buildEndpoint(provider, region)` constructs the canonical endpoint URL and auto-fills
   the endpoint field. The endpoint field shows "Auto-filled from provider and region".

3. **Provider override change**: re-runs both directions — re-extracts region from the
   current endpoint using the new provider, and rebuilds the endpoint from the new provider
   + current region if the endpoint is not user-owned.

The region field is **always rendered** (the conditional `needsRegion` hide is removed)
so auto-filled values are visible and editable at all times.

**Circular update prevention**: a `userEditedRef` tracks which fields the user has
directly typed into. Inference only flows *from* user-edited fields *into* non-user-edited
fields. Editing an inferred field marks it as user-owned and stops inference from writing
into it again.

---

## `buildEndpoint(provider, region)` — source verification

New export in `src/lib/provider.js`. Returns the canonical HTTPS endpoint URL for a
given provider + region string. Returns `null` when the combination cannot be inferred
from region alone.

### Backblaze B2

Template: `https://s3.{region}.backblazeb2.com` — no exceptions.

Known regions: `us-west-002`, `us-west-004`, `us-east-005`, `eu-central-003`,
`ca-east-001` (and legacy `us-west-001`). All follow the template.

Source: https://www.backblaze.com/docs/cloud-storage-data-regions (cited in
`docs/review-v1.14.0/06-providers/backblaze-b2.md`, fetched 2026-06-04)

### Wasabi

Template: `https://s3.{region}.wasabisys.com`

**Exception**: `us-east-1` → `https://s3.wasabisys.com` (legacy bare endpoint with no
region segment in hostname). This is the documented behaviour: the bare `s3.wasabisys.com`
hostname is the US East 1 endpoint and continues to work alongside the canonical
`s3.us-east-1.wasabisys.com`.

Full region list (16 regions): `us-east-1`, `us-east-2`, `us-central-1`, `us-west-1`,
`us-west-2`, `ca-central-1`, `eu-central-1`, `eu-central-2`, `eu-west-1`, `eu-west-2`,
`eu-west-3`, `eu-south-1`, `ap-northeast-1`, `ap-northeast-2`, `ap-southeast-1`,
`ap-southeast-2`.

Legacy alias hostnames (`s3.nl-1.wasabisys.com` etc.) are handled separately by
`extractRegion`'s `WASABI_ALIASES` map. `buildEndpoint` accepts canonical region names
only; typing a legacy alias slug like `nl-1` builds `https://s3.nl-1.wasabisys.com`
(valid alias, works correctly because `extractRegion` then maps it back to `eu-central-1`
for SigV4 signing).

Source: https://docs.wasabi.com/docs/what-are-the-service-urls-for-wasabi-s-different-storage-regions
(cited in `docs/review-v1.14.0/06-providers/wasabi.md`, fetched 2026-06-04; re-confirmed
live 2026-06-07)

### AWS S3

Template: `https://s3.{region}.amazonaws.com` — no exceptions for the standard
path-style service endpoint format, which is what Bucketer's form expects.

Virtual-hosted (`{bucket}.s3.{region}.amazonaws.com`) and dualstack
(`s3.dualstack.{region}.amazonaws.com`) forms are handled by `extractRegion` but are
NOT generated by `buildEndpoint`; the standard form is recommended for use as a
Bucketer endpoint.

Source: https://docs.aws.amazon.com/general/latest/gr/s3.html (cited in
`docs/review-v1.14.0/06-providers/aws.md`, fetched 2026-06-04)

### DigitalOcean Spaces

Template: `https://{region}.digitaloceanspaces.com` — no exceptions.

Known regions: `nyc3`, `sfo2`, `sfo3`, `ams3`, `sgp1`, `lon1`, `fra1`, `tor1`,
`blr1`, `syd1`, `atl1`, `ric1`.

Source: https://docs.digitalocean.com/products/spaces/details/availability/ (cited in
`docs/review-v1.14.0/06-providers/digitalocean-spaces.md`, fetched 2026-06-04)

### Cloudflare R2 — `null`

R2 endpoints encode the Cloudflare **account ID**, not the region:
`https://<account-id>.r2.cloudflarestorage.com`. Region is always `'auto'` regardless
of endpoint. `buildEndpoint` cannot construct an R2 URL from region alone.

Special handling: when the provider override changes *to* R2 and the region field is not
user-edited, the region is auto-filled with `'auto'` (since R2 always uses this value).
When it changes *away from* R2, the inferred `'auto'` is cleared.

Source: https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/ (cited in
`docs/review-v1.14.0/06-providers/cloudflare-r2.md`, fetched 2026-06-04)

### MinIO, Generic — `null`

Custom deployments with no standard hostname pattern.

## State model

```
form state (existing fields) +
  _infEndpoint: boolean   // endpoint was auto-filled, show inferred indicator
  _infRegion:   boolean   // region was auto-filled, show inferred indicator

userEditedRef (ref, not state) +
  endpoint: boolean       // user has directly typed/pasted into the endpoint field
  region:   boolean       // user has directly typed/pasted into the region field
```

`userEditedRef` is a ref (not state) because it does not affect rendering — it is
purely a guard for the inference logic. `_infEndpoint` and `_infRegion` are in form
state because they drive the inferred-marker UI.

Initial values for `userEdited`:
- `endpoint = !!initial.endpoint` — pre-filled endpoint is treated as user-owned so
  inference never overwrites it without user action.
- `region` — true only when `initial.regionOverride` is set AND differs from what
  `extractRegion` would return for the stored endpoint. If the stored region matches
  auto-extraction, treat it as inferred-on-load (so endpoint changes can update it).

## Inference rules (inside `applyChange` helper)

```
applyChange(prev, fieldKey, newValue):
  mark fieldKey as user-edited in userEditedRef
  clear _infEndpoint if fieldKey === 'endpoint'
  clear _infRegion   if fieldKey === 'regionOverride'

  if fieldKey === 'endpoint' && !userEdited.region:
    prov = providerOverride || detectProvider(endpoint)
    extracted = extractRegion(endpoint, prov)
    if extracted:            → fill regionOverride=extracted, _infRegion=true
    elif prev._infRegion:    → clear regionOverride='', _infRegion=false

  if fieldKey === 'regionOverride' && !userEdited.endpoint:
    prov = providerOverride || detectProvider(endpoint) || null
    built = prov && value ? buildEndpoint(prov, value) : null
    if built:                → fill endpoint=built, _infEndpoint=true
    elif !value && prev._infEndpoint: → clear endpoint='', _infEndpoint=false

  if fieldKey === 'providerOverride':
    newProv = newValue
    if prev._infRegion && prev.regionOverride === 'auto' && newProv !== R2:
      → clear regionOverride='', _infRegion=false   // R2-specific 'auto' no longer valid
    if !userEdited.region && endpoint:
      extracted = extractRegion(endpoint, newProv || detectProvider(endpoint))
      if extracted: → fill regionOverride=extracted, _infRegion=true
    if !userEdited.region && newProv === R2:
      → fill regionOverride='auto', _infRegion=true
    if !userEdited.endpoint && regionOverride && newProv:
      built = buildEndpoint(newProv, regionOverride)
      if built:            → fill endpoint=built, _infEndpoint=true
      elif prev._infEndpoint: → clear endpoint='', _infEndpoint=false
```

## Visual indicator

Inferred fields show a `.hint` span beneath the input:
- Endpoint: "Auto-filled from provider and region"
- Region: "Auto-filled from endpoint URL"

The hint disappears the moment the user edits the field (because editing marks the field
as user-owned and clears `_infEndpoint`/`_infRegion`). No new CSS class is needed; the
existing `.hint` styling is used.

The existing endpoint hint "Detected: Backblaze B2 · Region: us-west-004" is simplified
to "Detected: Backblaze B2" — the region is now shown in the region field itself.
